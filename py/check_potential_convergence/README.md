# Проверка сходимости потенциала: шаг 1A

`check_potential_convergence.py` проверяет **гравитационное поле**, а не penalty.
Запускается обычным Python с установленной AGAMA, в том числе локально от
пользователя `gala`. Docker, torch, BoTorch, CVXOPT и каталог скоростей не нужны
самому инструменту (у установленного пакета AGAMA могут быть свои зависимости).

Не вызываются `agama.orbit`, выборка IC, `solveOpt`, storage, сеть, rclone или
shutdown. Не создаются `.npz`, checkpoints и строки в общем пуле. Не меняются
RNG, глобальные единицы AGAMA, исходные модели и научный контракт. Этот инструмент
не запускает Step 1B (влияние настроек потенциала на penalty); подготовительный
интерфейс Step 1B без орбит описан отдельно в §6.

## 1. Запуск локально от gala

Все команды этого раздела пользователь выполняет самостоятельно, уже в сессии
`gala`, тем Python, в котором работает его AGAMA. Скрипт не переключает
пользователя, не использует sudo и не устанавливает пакеты.

Требуются Python >= 3.9, NumPy и SciPy; для графиков — Matplotlib. Pytest нужен
только разработчику для тестов. Не использовать `.venv-ai` для настоящего
AGAMA-прогона: в ней нет AGAMA.

Если исходный каталог доступен для чтения:

```bash
PYTHON=python3
CHECK=/home/wind/Agama/py/check_potential_convergence/check_potential_convergence.py
"$PYTHON" -c 'import agama, numpy, scipy; print(agama.__file__)'
"$PYTHON" "$CHECK" --help
```

Если этот путь недоступен пользователю `gala`, скопировать папку инструмента в
доступное место и изменить `CHECK`. Для основной проверки дополнительно передать
`--harness /полный/путь/Fornax_P21_PCA_w3Sersic_orblib_exp.py`. Этот файл только
читается через AST, **никогда не импортируется и не выполняется**. Для `--self-test`
он вообще не нужен. Не требуется переносить `table3.dat` или orbit libraries.

### Сначала: самостоятельная проверка установленной AGAMA

```bash
"$PYTHON" "$CHECK" --self-test --threads 1 \
    --output "$HOME/potential_checks/smoke_$(date +%Y%m%d_%H%M%S)"
```

Она проверяет аналитическую силу Plummer в единицах G=1, строит её Multipole,
экспортирует реальные узлы, загружает экспорт обратно и сравнивает силы.
**Орбиты не интегрируются.** Нормальный результат — `pass`, код 0.
В отчёте сохраняются путь/версия AGAMA и SHA256 её загруженных модулей. Поле
`binary_fingerprint_present` показывает, удалось ли зарегистрировать бинарный
модуль; совпадение с VM нужно проверять по её fingerprint, оно не предполагается.

### Затем: подготовить модели и проверить вход без AGAMA

В отдельный локальный файл поместить выбранные модели, по одной на строку:

```text
incl Q gh rh rho0 Upsilon
```

Это описание колонок, не строка заголовка. Непосредственно в файле нужны числа;
комментарии начинаются с `#`, после чисел допустима метка `# имя модели`.
Поддерживаются также существующие форматы с 9, 10 или 11 колонками:
`out_*`/`4Ups*`, `J_factor_*`, `Jcomputed_*`. Входные строки и номера строк
сохраняются в отчёте. Повторные строки не удаляются и не объединяются.
Ошибочные непустые строки, NaN/Inf, недопустимый наклон и выход за текущие границы
harness прекращают запуск; нет ни молчаливого пропуска, ни clipping.

Для научной проверки рекомендуется выбрать из **фактических результатов**
сферические контрольные точки старого, промежуточного и большого радиуса, а также
free-Q reference при том же наклоне. Не зашивать их числа в отслеживаемые файлы.
Если файл лежит рядом с инструментом, назвать его `models.local.txt`: он исключён
в локальном `.gitignore` этой папки. Возможен любой внешний входной файл.

У файлов запланированных probe-моделей Upsilon и penalty могут быть только
reference от другой точки, а не вычисленным результатом этой строки. На поле
в родных единицах это не влияет, но для физического масштабирования следует
брать Upsilon из соответствующей завершённой оценки.

```bash
MODELS="$HOME/models_potential_check.txt"
"$PYTHON" "$CHECK" --models "$MODELS" --validate-inputs
```

`--validate-inputs` не импортирует AGAMA и не создаёт выходной каталог.

### Основная проверка поля

```bash
"$PYTHON" "$CHECK" --models "$MODELS" --threads 1 \
    --output "$HOME/potential_checks/fields_$(date +%Y%m%d_%H%M%S)"
```

При копировании только папки инструмента добавить `--harness` к обеим командам.
Если Matplotlib отсутствует, добавить `--no-plots`: JSON, TSV и коэффициенты
всё равно будут записаны. Каждый запуск требует **нового** выходного каталога,
даже если старый пуст. Resume/overwrite отсутствуют. Родительские каталоги
создаются при необходимости; для gala рекомендуется вывод в его `$HOME`.

Без `--output` используется `runs/<UTC timestamp>` рядом со скриптом. `runs/`
исключён из Git, но пользователь должен иметь право записи в папку инструмента.
Не направлять вывод в отслеживаемые каталоги публичного репозитория.

## 2. Что именно сравнивается

Рецепт плотностей, исходные параметры Multipole, границы и единицы читаются из
harness через ограниченный AST-разбор арифметических выражений. Неизвестные
выражения и изменённая формула звёздной депроекции требуют явного пересмотра
диагностики, а не выполняются как Python-код.

Проверяется исходный потенциал интегрирования: `densitynorm=rho0`, звёздная масса
`massSt`, G=1. **Upsilon не умножается на плотности при построении.** Для перехода
к физической силе множитель равен `Upsilon * vscale**2` в (км/с)^2/кпк на единицу
выведенного ускорения; он сохранён в `units.physical_acceleration_factor`.
Все поля, разности и TSV остаются в исходных единицах, без этого множителя.

Для каждой строки строятся:

- `baseline`: точное воспроизведение текущего общего Multipole;
- `stars_baseline`, `halo_baseline`: отдельные компоненты с теми же настройками;
- `auto_n*`: изменение числа узлов с автоматическими границами;
- `radial_n*`: изменение только числа узлов, границы взяты из **экспорта baseline**;
- `angular_l*`: изменение lmax при фиксированных числе узлов и границах;
- `range_x2`, `range_x4`: расширение обеих границ сетки с сохранением или небольшим
  увеличением плотности узлов по log(r);
- `common_fine`: общий плотный Multipole для сравнения с суммой компонент;
- `split_baseline`: сумма полей двух baseline-компонент.

`rmin/rmax` — границы интерполяции, **не обрезание гало**. Физическая экспоненциальная
отсечка неизменна во всех сериях. Все фактические сетки экспортируются в `.ini`.

По умолчанию `--radial-nodes 23,46,92,184`,
`--angular-orders 4,8,12,16,24`, `--radii 96`, `--angles 9`.
Проверочные радиусы 0.001–110 кпк дополнены узлами и геометрическими серединами
интервалов трёх baseline-сеток. Направления покрывают меридиональный квадрант,
включая экватор и ось; это достаточно для принятой осесимметричной,
отражательно-симметричной плотности. Начало координат исключено.

## 3. Эталон и критерии

При **Q=1** сила гало независимо вычисляется SciPy-квадратурой плотности Zhao:
`M(<r)=4*pi*integral(rho(s)*s^2 ds)`, `a=-M(<r)*x/r^3` в G=1.
Потенциал учитывает также интеграл внешних оболочек до бесконечности, включая
мягкую отсечку. Квадратура повторяется с более строгой точностью. Формула не
использует плотность или массу, восстановленную из проверяемого Multipole.

Звёздное поле и гало при **Q != 1** имеют численный, не аналитически точный эталон.
Для каждой компоненты независимо проверяются:

1. удвоение числа интервалов при фиксированных границах и lmax;
2. увеличение lmax на 8 при уточнённой радиальной сетке (сферическому гало не нужно);
3. расширение границ вдвое при сохранении log-шага.

Границы эталонных сеток включают baseline и запас относительно проверочных радиусов.
Последний вариант становится эталоном только при прохождении этих проверок.
Для Q=1 независимая квадратура остаётся эталоном гало, даже если его численный
Multipole не сошёлся; это видно в `halo_ref_vs_reference`. Звёздный эталон всё
равно обязан сойтись. Совпадение разных Multipole не доказывает отсутствие всех
общих ошибок AGAMA; особенно это относится к сплюснутому гало.

Основная ошибка — `|a_test-a_ref|/|a_ref|`, а не деление на отдельную компоненту,
которая может обращаться в ноль на оси. Дополнительно выводятся ошибки компонент
с тем же знаменателем и разности потенциалов относительно точки (1,0,0) кпк.
Постоянное смещение потенциала не создаёт ложной ошибки его разностей.

Метрики отдельно для `central` (до 0.05 кпк), `main` (0.05–2.1),
`outer_orbits` (2.1–10), `halo_tail` (от 10) и `all`. Граничные точки могут
участвовать в соседних группах. Названия областей — диагностические: 2.1 кпк не
является трёхмерной границей орбит. RMS и квантили **не взвешены** по звёздной
плотности или наблюдательным ошибкам; конечная сетка не проверяет все орбиты.

Предварительные инженерные пороги: RMS <= 1e-4, максимум <= 1e-3. Для сходимости
самого эталона оба порога в 10 раз строже. Можно явно задать `--rms-tol` и
`--max-tol`; значения сохраняются в отчёте. Они не переводятся в sigma или CI.

Общий `status` модели проверяет baseline на **всех** пробах (`all`), а
`comparisons.baseline.main_status` — только `main`. Потенциальные разности
сохраняются для диагностики, но не входят в force-based pass/fail.
`field_only_candidate` выбирает прошедшую конфигурацию по условной стоимости
`N*(lmax+1)^2`, не по измеренной скорости; он ничего не меняет в harness.

Если `reference_unconverged`, изучить `reference.stars/halo.checks`, не ослаблять
порог только ради pass. При необходимости повторить в **новом каталоге**, например:

```bash
"$PYTHON" "$CHECK" --models "$MODELS" --threads 1 \
    --radial-nodes 23,46,92,184,368 --angular-orders 4,8,16,24,32,48 \
    --output "$HOME/potential_checks/refined_$(date +%Y%m%d_%H%M%S)"
```

Это только проверка поля. Ни `pass`, ни улучшение поля не устанавливают
неизменность penalty. Для этого требуется отдельно согласованный шаг 1B.

## 4. Артефакты и коды завершения

В корне вывода: `report.json` с параметрами запуска, SHA256 скрипта/harness/входа,
идентификацией AGAMA, smoke test и состоянием каждой модели; `smoke_plummer.ini`.
Каждый `model_000/`, `model_001/`, ... содержит:

- `report.json`: рецепт плотностей, эталон, все метрики, реальные узлы, кандидат;
- `errors.tsv`: координаты, векторные/компонентные ошибки, разности потенциалов;
- `*.ini`: коэффициенты каждого построенного Multipole;
- при включённых графиках `force_errors.png`, `error_map.png`, `radial_grids.png`.

Метки моделей не используются как пути. Промежуточный верхний отчёт обновляется
атомарно. При ошибке или Ctrl-C он содержит `failed` и причину; уже записанные
коэффициенты и результаты остаются. При жёстком убийстве процесса последняя
стадия может остаться `running` — это не успешное завершение.

| Код | Значение |
|---|---|
| 0 | Вход проверен, smoke test прошёл либо все baseline-поля прошли проверку |
| 1 | Ошибка исполнения/импорта/прерывание; смотреть `error` и частичный отчёт |
| 2 | Неверные параметры/вход либо выходной каталог уже существует |
| 3 | Диагностика завершена, но `needs_refinement` или `reference_unconverged` |

При коде 3 отчёты — полезный результат, а не сбой вычисления. Для анализа прислать
верхний `report.json`, модельные `report.json` и графики. Для проблемы запуска —
сообщение stderr и частичный отчёт. Повторно запускать поиск/orblib не требуется.

## 5. Локальные тесты разработчика (без AGAMA)

Из данной папки в основном репозитории:

```bash
../../.venv-ai/bin/python -m pytest -q test_potential_convergence.py test_potential_pair.py \
    --rootdir=. --import-mode=importlib -p no:cacheprovider
python3 -m py_compile check_potential_convergence.py test_potential_convergence.py \
    run_potential_pair.py test_potential_pair.py
```

Тесты проверяют математику (включая Plummer, гармонический предел, cusp и отсечку),
AST-рецепт, форматы входа, независимость серий сеток, полный драйвер на fake AGAMA,

Они не подменяют реальный `--self-test` и проверку моделей в установленной AGAMA.
Не запускать pytest из корня репозитория: локальный `py/` затеняет модуль pytest.

## 6. Step 1B: подготовка и preflight без орбит

`run_potential_pair.py` — отдельный инструмент. Его CLI допускает **только**
`--validate-inputs` или `--preflight`; режима запуска пилота/орбит нет.
Проверка Step 1A выше не менялась. Расширения экспериментального harness не меняют
его обычные параметры потенциала, выборку IC, поиск Upsilon или storage keys.
Production, исходные результаты и научный контракт остаются неизменными.

### Где выполнять

| Проверка | Окружение | Что не выполняется |
|---|---|---|
| Mock/numeric-тесты и `--validate-inputs` | локальная `.venv-ai`, NumPy/SciPy/pytest | импорт AGAMA/harness, орбиты, solveOpt |
| `--preflight` | локальный Python с полным набором зависимостей harness | выборка IC, seeding AGAMA, орбиты, solveOpt, сеть |
| Будущий научный пилот | отдельно согласованное окружение и ресурсы | этот CLI пока не умеет его запускать |

Для preflight нужны не только AGAMA/NumPy/SciPy, но и зависимости импортируемого
harness: torch, BoTorch/GPyTorch, sklearn, requests и пакетные модули AGAMA.
Полный solver/backend проверяется будущим пилотом, не preflight. VM не обязательна:
подойдёт локальное рабочее окружение AGAMA. Новые пакеты инструмент не устанавливает.

### Проверка входов без AGAMA

Требуется точный файл моделей и **модельный** `model_NNN/report.json` от плотной
Step 1A проверки выбранной строки. Нумерация `--model-index` начинается с нуля.
Вместе с отчётом должны оставаться соседние `.ini` и верхний `report.json`.

```bash
ROOT=/path/to/Agama
CHECK="$ROOT/py/check_potential_convergence/run_potential_pair.py"
HARNESS="$ROOT/py/Fornax_P21_PCA_w3Sersic_orblib_exp.py"
MODELS="$HOME/models_potential_check.txt"
FIELD_REPORT=/path/to/dense/model_000/report.json

"$ROOT/.venv-ai/bin/python" "$CHECK" \
    --models "$MODELS" --model-index 0 --field-report "$FIELD_REPORT" \
    --harness "$HARNESS" --validate-inputs
```

Выход — JSON в stdout, без создания файлов. Проверяются формат/bounds моделей,
точное совпадение выбранной строки с field report, сходимость reference, прохождение
`angular_l24` во всех регионах, плотность проб и прежние пороги. Проверяется интерфейс
актуальной экспериментальной копии harness; production и старая копия без hook
отклоняются до импорта. `dependencies` показывает наличие пакетов, не успешность
их импорта или работоспособность AGAMA solver.

Изменение SHA256 harness после добавления hook ожидаемо: физический recipe
сравнивается отдельно от пути/хэша исходника. Оба хэша сохраняются. Изменившиеся
физические определения, сетки или коэффициенты не принимаются молча.

### Настоящий preflight, всё ещё без орбит

В пользовательском окружении с зависимостями, после проверки входов:

```bash
PYTHON=python3
"$PYTHON" "$CHECK" \
    --models "$MODELS" --model-index 0 --field-report "$FIELD_REPORT" \
    --harness "$HARNESS" --threads 1 --preflight \
    --output "$HOME/potential_checks/pair_preflight_$(date +%Y%m%d_%H%M%S)"
```

Вывод всегда в **новый** каталог. Runner импортирует только экспериментальный
harness, в изолированном рабочем каталоге, без save/reuse/stream/resume. Каталог
звёзд берётся из `table3.dat` рядом с этим harness; его SHA256 фиксируется.
Подготовка наблюдений и фиксированный GH-bootstrap остаются штатными. Callback
вызывается сразу после построения baseline, до IC/orbit/library/solve/history.

Проверяются AGAMA binary fingerprint относительно field evidence, фактические
сетки и точное совпадение экспортов A/B с прежними файлами. A — исходный N=23,lmax=4;
B — N=184,lmax=24 с границами **из baseline**, не auto-grid. Для сравнения полей
независимо строятся live-потенциалы из архивного recipe/модели/настроек Step 1A,
без использования плотностей, переданных harness, и без умножения на Upsilon.

В `potentials.A` и `.B` теперь три раздельных сравнения:

| Поле отчёта | Что сравнивается | Участие в pass/fail |
|---|---|---|
| `live_reproduction` | live harness и независимая live-реконструкция Step 1A | максимум <=1e-9 |
| `export_roundtrip` | текущий экспорт после загрузки и live harness | численная разность информационная, не критерий воспроизведения |
| `serialized_reproduction` | текущий и архивный экспорты, оба после загрузки | максимум <=1e-9 |

В каждом сравнении: all RMS/max, `scores` по регионам, координаты/радиус максимума,
`tolerance=1e-9`, `within_reproduction_tolerance`, `gates_preflight` и явный reference.
Разности нормированы на силу соответствующего reference; у roundtrip это live-поле.
`grid_matches_evidence` и `export_matches_evidence` тоже обязательны для pass.
Порог 1e-9 не ослаблен: исправлен объект сравнения. Научные пороги Step 1A неизменны.

`export()` AGAMA не является точной копией внутренних массивов: он повторно
восстанавливает гармоники, удаляет малые коэффициенты и округляет текст. Поэтому
нельзя считать live-to-reloaded сравнением двух одинаково построенных live-полей.
Верхнее `serialization_warnings` перечисляет A/B, где roundtrip превышает 1e-9;
это видно и в stdout. Ненулевая конечная ошибка roundtrip сама по себе не блокирует
live-проверку, но повреждённый файл, неверная сетка/hash или невалидные силы дают отказ.
**`preflight_pass` не разрешает подменить рабочий live-потенциал загруженным `.ini`.**

Артефакты: `report.json`, `preflight.log`, `A.ini`, `B.ini`. Успех —
`status=preflight_pass`; `orbit_calls=0`, `ic_sampled=false`, `penalty_checked=false`,
`solver_checked=false`, `ic_admissibility_checked=false`, `library_created=false`.
Это не подтверждение работоспособности полной библиотеки или оценки памяти пилота.
Контекст сохраняется до проверки полей; `stage` и частичные метрики каждой ветви
пишутся последовательно, до возможного исключения. Статусы ветвей: not_checked,
running, pass, failed/interrupted. Обычная ошибка A не мешает проверить B; прерывание
останавливает работу. В failed report остаются причина и уже измеренные значения.
Коды: 0 — проверка прошла; 1 — ошибка preflight; 2 — вход/путь/существующий output.

### Что уже проверяет mock-драйвер и что отложено

Тестируемое ядро `evaluate_pair` не вызывается CLI. На fake AGAMA оно проверяет:
общие точные IC/time для A/B, отдельные native IC/time, проверку boundness без
clipping/resampling, одинаковые dtype/полный solve, фиксированную и найденную
Upsilon, перекрёстные solve, исключения и частичные результаты при STOP.
Общий `solve_orbit_library` используется и штатным harness: паритет формулы
проверен для float32/float64 без копирования научного evaluator в runner.

Диагностические матрицы сохраняются как отдельные `.npy` и читаются через mmap;
существующий `.npz` writer/storage не меняется. Manifest включает контекст,
коэффициенты, seed, IC/time hashes, настройки интегрирования/solve и dtype;
checksum проверяется перед чтением. Веса, предсказания и невзвешенные остатки
линейных constraints сохраняются отдельно. Никаких out_*/4Ups*, shared catalog,
автоматической выгрузки, удаления или запуска существующих launchers.

Сводка пар не смешивает физические модели; показывает неполные, failed и повторные
seed, не удаляя записи. Приближённый t-интервал описывает только средний MC-сдвиг,
не неопределённость параметров Fornax; практический допуск автоматически не применяется.

Пока не предоставлены: CLI научного пилота/пакетный scheduler, resume серии,
облачная доставка и автоматическое решение по Q29. Будущий pilot entry point
должен передавать проверенный runtime manifest, сохранять ресурсы/время и связывать
контроли A/A, native и более точный C с утверждённым планом. Construction mode
(live density или loaded export) должен быть явным в контексте: hash текста
коэффициентов сам по себе не доказывает идентичность внутренних полей.
Реальные IC, solver, орбитальное покрытие и ресурсы ещё надо проверить после
отдельного разрешения.
